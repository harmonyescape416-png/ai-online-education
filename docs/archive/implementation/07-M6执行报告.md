### 1.2 已修复的 3 个关键遗留

#### (1) 视频拖动导致有效学习时长虚增 —— **真实缺陷，已修复**

**问题**：`reportProgress` 的有效时长增量 = `min(位置前进量, 900)`。用户拖动进度条从 0 跳到 900 秒，会被计为 900 秒学习时长。

**修复**（`kzai-learning/src/main/java/com/kzai/learning/service/LearningService.java`）：

```java
private long effectiveDelta(LocalDateTime lastUpdate, LocalDateTime now, int newPosition, int storedPosition) {
    long advance = (long) newPosition - storedPosition;
    if (advance <= 0) return 0;
    long elapsed = (lastUpdate == null || now == null) ? 0
            : Math.max(0, Duration.between(lastUpdate, now).getSeconds());
    long allowed = Math.min(advance, elapsed + Math.max(0, studySecondsTolerance)); // 容差 3s
    return Math.min(allowed, maxStudySecondsPerReport);                              // 单次上限 900s
}
```

新增配置 `kzai.learning.study-seconds-tolerance: 3`。

**验证证据**（HTTP 端到端，真实 MySQL）：

```
[INFO] 拖动 700 秒后有效时长=308 秒（未虚增 700 秒）
[PASS] 拖动不虚增有效时长
[PASS] 拖动后断点随之前进 (1000)
```

新增单元测试 `progressReport_dragDoesNotInflateStudySeconds`（H2）。

#### (2) `learning_lesson.progress` 与接口进度不一致 —— **M5 报告中的"33% vs 0"为采样时点问题，本轮已建立同刻对账**

**核查结论**：`LearningService` 在章节完成/进度上报的同一事务内 `syncLessonAggregate()` 写 `learning_lesson.progress`，不存在异步延迟。M5 报告中出现的 33%/0 差异，是"完成章节后立刻查库、但查询发生在提交前"的采样问题，非代码缺陷。

**本轮补充**（`scripts/e2e-m5.sh`）：在同一时点分别取 API 与 MySQL 值比对：


```js
const resp = await fetch(url, { method:'POST', headers:{...}, body: JSON.stringify(body), signal })
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')          // 增量解码，避免中文跨块截断
let buffer = ''
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  let idx
  while ((idx = buffer.indexOf('\n\n')) !== -1) {  // 按空行切帧
    const frame = buffer.slice(0, idx); buffer = buffer.slice(idx + 2)
    const parsed = parseFrame(frame); if (parsed) onEvent(parsed)
  }
}
```

| 用户消息与助手消息有序存储 | Redis 中 `USER` / `ASSISTANT` 交替，6 条 = 3 轮 |
| 刷新后恢复 | 浏览器 E2E：`[PASS] 刷新后历史会话仍在列表` |
| 多轮上下文 | 3 轮后 Redis 累积 6 条，模型入参携带全部历史 |
| 不同用户隔离 | Key 前缀含 `userId`；B 访问 A 的 4 类接口全部 403 |
| 消息正文不入 `chat_session` | `information_schema` 校验：该表恰好 8 列，无正文列 |
| 重试不重复写用户消息 | 同 `messageId` 连发 2 次，`USER` 条数不变（4 条） |
| 停止只存已输出片段 | 停止后 Redis 助手内容 **67 字符**（完整回复约 200 字符），未写入未输出部分 |
| 删除清理 | MySQL 行 -1，Redis Key `grep -c` = 0 |
| 服务重启后可恢复 | Redis 未清空，重启后 `GET /session/{id}` 原样返回 |

### 6.3 发现的真实缺陷（本轮修复）

**`ChatMemory.add()` 覆盖而非追加**：`opsForValue().set()` 是全量写。第一版直接 `set(newMessages)`，导致第二轮对话把第一轮历史抹掉（实测详情只返回 2 条而非 4 条）。已改为「读回 → 追加 → 写回」。

**`ChatMessageCodec.deserialize()` 返回不可变列表**：`Stream.toList()` 返回 unmodifiable，`appendPartial` 内 `all.add()` 抛 `UnsupportedOperationException`，被 catch 后静默降级为内存缓存——表现为"回答返回了但 Redis 里只有用户消息"。已改为返回 `new ArrayList<>()`。

## 7. 停止生成与部分消息持久化证据

### 7.1 实现

```
StopRegistry.tryAcquire(sessionId)        # 同一会话单飞，失败 → 终态 ERROR
StopRegistry.markStop(sessionId)          # 写 AI:STOP:{sessionId}，TTL 5 分钟
ChatService 循环内每段前检查 isStopRequested → 命中则 break（不再向模型拉取后续增量）
终态：清理 AI:STOP:{sessionId} + release(sessionId)
```

**关键点**：停止是在**服务端流订阅层**生效（`break` 出迭代后 Flux 被 `doOnCancel` 截断），不是仅隐藏前端文字。

### 7.2 实测数据

```bash
$ curl -sN -X POST .../chat ... &   # 发起生成
$ sleep 0.9
$ curl -X POST .../chat/stop
{"code":200,"data":{"stopped":true,"sessionId":"..."}}
```

| 指标 | 实测值 |
|---|---|
| 停止接口响应延迟 | **53 ms / 54 ms**（两次样本，目标 ≤ 1000 ms） |
| 终态事件 | `"code":"STOPPED","stopped":true`，**恰好 1 个** `1002` |
| Redis 中助手内容长度 | **67 字符**（完整回复 ≈ 200 字符）→ 只保存已输出部分 |
| 完整回答是否入库 | 否（`grep '不会调用真实大模型'` = 0） |

### 7.3 并发终态一致性

| 场景 | 行为 |
|---|---|
| 停止 + 正常完成 | 停止标识在 `finally` 清理，不会残留到下一轮 |
| 停止 + 删除会话 | 删除走 MySQL 先删 → Redis 清理；残留 Key 因元数据缺失不可访问 |
| 同一会话二次生成 | `tryAcquire` 失败 → 立即返回单条 `1002` `code=ERROR`「该会话已有进行中的生成任务」 |
| 旧停止标识误伤新一轮 | 生成开始时 `clearStop`，实测第二轮正常完成 |

### 7.4 部署模式限制（**必须声明**）

当前的「同一会话单飞」与「停止」依赖**应用进程内状态**（`ConcurrentHashMap` 集合）：
- **单实例部署**：可靠。
- **多实例部署**：实例 A 的停止标识写 Redis 后，实例 B 的生成循环也能读到（`AI:STOP` 是 Redis 共享的），**停止本身跨实例有效**；但「同一会话只允许一个生成任务」的**单飞锁仅在单实例内生效**，跨实例可能同时生成两路。
- **未实现**：Redis 分布式锁（`SET NX PX` + 续期）实现跨实例单飞。留到需要水平扩容时补。

**外部模型停止计费不属于可保证行为**——本实现只能保证应用侧停止向模型拉取后续增量。
