```java
// org.springframework.ai.chat.client.ChatClient（1.0.0-M6）
ChatClientRequestSpec functions(FunctionCallback...)   // 请求规格级工具注册
ChatClientRequestSpec toolContext(Map<String,Object>) // 可信上下文
StreamResponseSpec chatResponse()                     // Flux<ChatResponse>（读 usage）
CallResponseSpec   chatResponse() / content()

// org.springframework.ai.model.function.FunctionCallback
Builder.function(String, BiFunction<I,ToolContext,O>) → description(String)
        → inputType(Class) → build()

String call(String toolInput); default String call(String, ToolContext)

// org.springframework.ai.chat.model.ToolContext
Map<String,Object> getContext()

// org.springframework.ai.model.function.FunctionCallingOptions
setFunctionCallbacks(List) / setToolContext(Map) / proxyToolCalls(Boolean)

// org.springframework.ai.chat.messages.AssistantMessage（M6 取文本是 getText()）
getText() / hasToolCalls() / getToolCalls()
```

**关键兼容性发现（D7-2）**：反编译 `AdvisedRequest.toPrompt()` 证明——M6 ChatClient **仅在 Prompt 的 options 为 `FunctionCallingOptions` 时**才把 functions/toolContext 合入模型请求；普通 `new Prompt(messages)` 的运行时回调会被**静默丢弃**（options 实际类型为 `DefaultChatOptions`，已被桩模型测试捕获）。因此 `DashScopeChatProvider.streamWithTools` 显式构造：

```java
FunctionCallingOptions options = FunctionCallingOptions.builder()
        .functionCallbacks(tools)          // M6 Builder 签名
        .toolContext(toolContext)
        .proxyToolCalls(Boolean.TRUE)      // 模型内部执行工具并续轮
        .build();
chatClient.prompt(new Prompt(messages, options)).stream().chatResponse()...
```

该行为由 `DashScopeToolPlumbingTest` 锁定（4 个用例，含「普通 Prompt 丢弃回调」的陷阱回归）。

### 2.3 工具执行线程与身份

模型发起工具调用 → AbstractToolCallSupport 在流内执行 `FunctionCallback.call(args, ToolContext)` → 工具从 ToolContext 取**可信 userId/roles/requestId/sessionId** → `UserContext.set(...)` 恢复 → Feign（`InternalAuthFeignInterceptor` 签名 + 身份头传播）→ `finally UserContext.clear()` 防线程池复用泄露。userId 任何时刻不接受模型参数。

## 5. ToolResultHolder 与结果隔离

- **实例级隔离**：每轮生成 new 一个实例，经 ToolContext 传递；不同用户/会话/轮次互不可见（单测 `isolation_perInstance`）。无任何全局静态变量。
- **有序保存**：同轮多工具结果按产生顺序排列；1003 按该顺序输出。
- **去重**：cardId（`course:{id}` / `order:{id}`）唯一——同实体一轮只发一张 1003；后续更完整载荷**就地合并覆盖**（如详情补章节数），位置不变。
- **失败不冒充成功**：失败工具只记审计（errorKind），不写入任何卡片。
- **持久化**：卡片随助手消息同一条 RPUSH 落入 `CHAT:{key}` List；Redis 失败时整条降级内存并 `persisted=false` 显式告知，不虚报已保存。
- **历史回放**：`GET /session/{id}` 返回助手消息 `cards` 数组；回放零工具调用。实测：

## 6. SSE 1003 事件与顺序

- 1001 文本增量（不变）→ 1003 卡片（去重后、失败工具无卡片）→ 1002 恰好一个。
- 实测顺序断言（e2e）：`1001×N → 1003×M → 1002×1`；1002 之后无任何事件；重复结果仅一张卡片（`cardCount==1003 帧数`）。
- 停止场景：只保留已完成且允许持久化的结果；未授权写操作被工具拒绝。
- SSE 中断/重连不触发第二次真实订单写入（提案消费 + 稳定 requestId + 交易幂等三层防护）。
- 未知事件类型前端静默忽略（`KNOWN_CARD_TYPES` 白名单，向前兼容）。
- M6 原有聊天/停止/历史/重命名全部回归通过（66+18+5）。
