### 2.1 缺陷：审计日志从未真正落库（M10 报告声明与实际不符）

- 现象：`sys_operation_log` 中 `CORRECT_REPLY` / `AI_REPLY` 计数为 **0**，但接口返回 200。
- 根因：`kzai-user` 的 `InternalUserController` 使用
  `Constants.INTERNAL_PATH_PREFIX("/internal/") + "/users"` → 实际路径 `/internal//users`（**双斜杠**），
  与 M6 起 aigc 同款历史缺陷；Feign 调 `/internal/users/operation-logs` 命中 405/500，
  而 `OperationAuditLogger` 设计为「审计失败不阻断业务」→ 长期静默失败。
- 修复：控制器改为字面路径 `/internal/users`；重启 user 后实测：
  **连续两次人工修正 → `CORRECT_REPLY` 2 条记录**（多次修正形成时间线，非仅最近一次快照）。
- 附带：全仓排查 `INTERNAL_PATH_PREFIX + ` 拼接，仅 `AigcClient`（`/internal/ai/generate`，无双斜杠）合法。

## 3. M9 重建原子性（故障注入）与修复

### 3.1 故障注入实测（修复前）

新增 IT 用例 `reindexCrashMidway_...`：文档 C 已发布切片 C_0/C_1；重建只写入新版本首片后崩溃。
结果：**旧切片仍可召回，但未发布的新切片也参与检索** → 新旧混用 / 部分覆盖（IT 红）。

### 3.2 最小修复方案（用户批准：表与索引架构不变，孤儿清理策略 C）

`indexVersion` 语义由「物理索引版本」复用为「**文档发布版本**」（MySQL `ai_knowledge_document.index_version` 为权威值，mapping 已有该 integer 字段）：

1. **重建前清理**：删除该文档「非当前已发布版本」的孤儿切片；
2. 写入**新版本切片**（`chunkId=docId_v{newVer}_{i}`，`indexVersion=newVer`），**不覆盖、不删除任何旧切片**；
3. `countByDocIdVersion(docId,newVer)` 数量核验（不等则失败重试，旧版本仍完整可用）；
4. **发布切换**：更新 MySQL `index_version=newVer`（单文档原子更新 = 发布动作）；
5. 发布后清理：删除该文档非 `newVer` 的切片（此时才允许破坏旧版本）；
6. **检索侧过滤**：`hit.indexVersion != doc.index_version` 的命中直接丢弃（未发布切片不可召回）；
7. **定时兜底**：新增 `OrphanChunkCleaner`（5 分钟一轮，按 MySQL 权威版本清理），与「重建前清理」构成双保险。

### 3.3 验证（修复后）

ES IT **7/7 通过**，故障注入用例断言三项：
- 旧版本切片仍可召回（不被破坏）；
- 未发布的新版本切片**不参与检索**；
- 发布切换后新版本可召回、旧版本不再召回。

## 5. 通知架构与服务归属

```
业务服务（learning / course）                     user 服务
┌──────────────────────────────┐            ┌──────────────────────────┐
│ 业务事务（同一本地事务）      │            │ /internal/notifications  │
│  业务表写入 + sys_event_outbox│  Feign     │  （内部签名 + 服务端身份） │
│  ─────── 提交后 ────────      │ ─────────► │  publish(eventKey,...)   │
│  NotificationOutboxWorker     │  相同       │  UNIQUE 去重 → 幂等       │
│  原子领取（租约）+ 指数退避   │  eventKey   │  sys_notification        │
│  失败保留行 / 重启恢复        │  重试       └──────────────────────────┘
└──────────────────────────────┘
```

- **职责边界**：user 只存通知与权限；learning/course 只生产事件，**不写通知表**；不引入 Kafka/RabbitMQ/新微服务。
- **可靠投递**：事件行与业务同库同事务（业务回滚 → 事件不产生）；Worker 原子条件更新领取（并发仅一个胜出）；
  失败退避重试（1/2/4/8 分钟上限 10 分钟，≤5 次）后置 FAILED 并保留 `error`/`request_id`；
  服务重启后 PENDING 与租约过期的 SENDING 自动恢复；**通知失败绝不回滚业务、绝不重复生成回复/审核记录**。
- **不用 Redis 临时 Key 代替持久化保障**（唯一约束 + 行状态是唯一依据）。

### 5.1 事件定义与 eventKey 幂等规则

| 类型 | 触发点（真实业务） | eventKey | 收件人 |
|---|---|---|---|
| `AI_REPLY` | `AiReplyTxService.completeGeneration` 事务内（任务置 SUCCESS 后） | `AI_REPLY:{replyId}` | 问题提出者 |
| `QUESTION_REPLY` | 教师回答（事务内）；学员回答/追问（事务内） | `QUESTION_REPLY:{replyId}` | 教师回答→提问者；追问→被追问回复作者（AI 回复不重复通知） |
| `COURSE_APPROVED` | `AuditService.approve` 事务内（审核记录写入后） | `COURSE_APPROVED:{auditId}` | 课程负责人 `course.creater` |

规则补充：
- 同一回复仅对应一个明确通知类型；**已触发 `AI_REPLY` 的 replyId 不再生成普通问答通知**（追问 AI 回复不重复通知）。
- 教师**普通文字修正**（`correct`）**不产生新通知**（避免重复骚扰），修正历史由 `sys_operation_log` 时间线承载。
- 审核通过以**真实审核记录**为依据（新审核通过 → 新事件）；驳回/失败/回滚不产生事件；
  不因「课程当前是已上架」在查询时重复发通知。
- MOCK 来源在标题与正文显著标识（`AI 已回复你的问题（MOCK 演示）` / `[MOCK 演示，非真实模型输出]`）。

## 6. 接口与权限

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/notifications` | 列表（创建时间倒序、分页、type、readStatus 筛选；仅本人未删除） |
| GET | `/notifications/unread-count` | 真实未读数 |
| GET | `/notifications/{id}` | 详情（首次打开自动已读） |
| PUT | `/notifications/{id}/read` | 单条已读（幂等，不覆盖首次 `read_time`） |
| PUT | `/notifications/read-all` | 全部已读（仅本人未读且未删除） |
| DELETE | `/notifications/{id}` | 接收者维度逻辑删除（幂等） |
| POST | `/internal/notifications` | 业务服务投递事件（内部签名；无签名 403） |

安全：
- 身份只取 JWT（`UserContext`），**不接收任何客户端 `recipientId`**；所有 SQL 强制 `recipient_id` 条件。
- 越权/不存在统一 **body.code=404**（受控，不泄露他人通知是否存在）；未登录 **401**；内部接口外部访问 **403**。
- 通知正文只含摘要（≤100 字 + 去换行），**不写入受保护讲义/全文**；前端纯文本插值渲染（默认转义，防 XSS）。
- 跳转目标为**站内固定路由**（`/questions`、`/teacher/courses/{id}/edit`），不使用通知携带的外部 URL。
- **用户删除**：`UserManageService.delete` 同库事务内 `deleteByUser` 清理其通知（无用户关联残留；单测验证不误删他人）。
