# 50-数据校验与状态同步修复报告（M15.15）

> 执行依据：用户《检查并修复后端与前端的数据校验及状态同步问题》指令（4 项：空白/超长校验、重复文本历史、搜索匹配简介、昵称头像回读）。完成后暂停等待验收。

## 1. 问题①：空白输入与超长内容后端拒绝（已修复）

核验：课程问答（@NotBlank/@Size 已有）；**AI 聊天缺口实锤**——ChatController 仅判 null（空白串通过、无长度上限）。

修复（ChatController streamChat + textChat 两入口）：
- text.isBlank() → 400「sessionId 与 message 均必填，且不能为空白内容」
- text.length() > 4000 → 400「消息内容过长（上限 4000 字）」
- text.strip() 后传服务层

实测：空白 → 400；4001 字 → 400「消息内容过长」。

## 2. 问题②：重复文本不生成多条历史（已修复）

核验：后端已有 messageId 幂等（RedisChatMemory.markOnce SETNX）——但前端 messageId=时间戳+随机（每次不同）→ 同文本重发仍产生多条。

修复（ChatService streamChat/callChat 入口 + RedisChatMemory 新方法）：
- isDuplicateWithinWindow(userId, sessionId, text, 2)：2 秒窗口内相同文本 → streamChat 以 SSE END 返回「请勿短时间内重复发送相同内容」（结构 terminal+TERM_ERROR 与既有错误一致）；callChat 抛 BizException——不写入历史
- 合法间隔重复不受影响（窗口仅 2 秒）；重复防护写 Redis（AI:DUP:{userId}:{sessionId}，2s TTL）

实测：第 1 次 200 MOCK 回复 → 0.5 秒后第 2 次 400 拒绝（未写入历史）→ 3 秒后合法重复 200 正常回复；会话标题自动命名仅一次。

## 3. 问题③：课程搜索匹配课程简介（已修复）

核验：/courses keyword 仅 like 课程名称。

修复（CourseService.page）：keyword 时 OR exists 子查询匹配 course_content.course_introduce（共键关联 cc.id=course.id、deleted=0 过滤、单引号转义防注入）；服务端分页前过滤（全量排序语义不变）。

实测：搜「单体到微服务」（简介内容，非名称）→ 命中 1 门「Java 微服务架构实战」。

## 4. 问题④：昵称/头像回读（非缺陷，为未实现功能——待批准）

核验：user 表字段 id/username/cell_phone/password/status/type——**无昵称/头像字段**（数据库设计原表即无；ProfileUpdateRequest 注释「姓名等字段原表不具备」）；前端 ProfileView 亦无昵称/头像输入——该功能当前不存在（原始需求 3.2.5 个人中心=改手机号/密码）。

定性：非缺陷。若需要该功能需您批准（涉及数据模型扩展）：

| 方案 | 内容 | 影响 |

| A（推荐） | 新增 user_profile_ext 表（user_id PK/nickname/avatar_url）——不改 12 核心表 | 新表+用户服务接口扩展+头像上传存储（本地/OSS） |
| B | 12 核心表 user 加列 | 违反纪律（不改核心表）——不推荐 |

前端回读逻辑（profile 接口返回 ext 字段+表单回显）在方案批准后实施。
