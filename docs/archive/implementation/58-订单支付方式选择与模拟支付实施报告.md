# 58-订单支付方式选择与模拟支付实施报告（M15.16）

> 执行依据：用户《订单提交页面支付方式选择与模拟支付》指令（微信/支付宝模拟支付，不对接真实 API）。
> **结果：提交订单→支付方式选择→模拟支付→已支付+开课+成功反馈全链路落地，E2E+DB 实测通过。完成后暂停等待验收。**

## 1. 后端（trade + learning）

| 接口 | 行为 |
|---|---|
| **POST /orders/{id}/pay**（新增） | 模拟支付：归属校验→仅待支付可支付（幂等：已支付返回 alreadyPaid+补开课）→条件更新防并发（status 1→2）→明细状态/渠道同步（order_detail.status=2 + pay_channel 落库）→开课（Feign learning 内部接口，事务提交后执行） |
| POST /internal/learning/enroll-for-paid（learning 新增） | 支付成功开课：enroll（learning_lesson 建档，幂等返回既有档案）；权益 resolve 依赖明细状态已支付 |

关键修复（3 项，实施中发现）：
1. **明细状态同步缺失**：enroll 权益判定链查 order_detail.status——原设计仅更新订单主表 → 明细停留待支付 → 开课被拒「未取得学习权益」——markPaid 同步明细状态（syncDetailPaid，幂等/正常分支统一调用）
2. **跨服务事务隔离**：enroll Feign 在 markPaid 事务提交前调用 → learning 回查 trade 读到未提交旧值 → 仍拒绝——**开课移入 afterCommit 回调**（事务提交后执行）
3. **幂等分支补开课**：重复 pay（alreadyPaid）也执行 afterCommit 补开课（首次开课失败的重试路径）

## 4. 开课状态语义说明

支付成功后 learning_lesson **status=1（学习中）**——进度 0%、按钮「开始学习」（M15.14-R5 已定性：有 lesson 记录=已加入）。用户需求的「待学习」语义由**进度 0%+开始学习按钮**承载（与 M15.14-R5 状态判定规则一致，未改学习状态枚举）。
